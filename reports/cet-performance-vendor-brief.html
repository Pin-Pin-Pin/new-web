四、請依此三個階段交付

下列為工作範圍。通過與否請用下一節「驗收標準」，不要用 PSI 總分 90。

P0 全站主題

第一階段：拿掉首屏阻塞

這是所有 header／footer 頁面分數差的共同原因，做一次全站受益。

  1. Drupal 10 主題 CSS aggregation：只在需要的路由載入 library。前台移除 book、toolbar、contextual、webform、tablesort、system-status、shortcut 等後台 CSS。
  2. 首屏關鍵 CSS 內聯或單一合併檔；其餘 CSS 延後。gtm.js、drupalSettings 不要擋首次繪製。
  3. 第三方改載入策略：GTM／gtag／Facebook／Matomo／LINE 在 window.load 後再注入，或只留一套分析。捐款頁可例外保留轉換像素，但仍應延遲。
P0 頁面資產

第二階段：LCP 圖片與字體

  1. 首頁 slider：只 preload 第一張；其餘 lazy。提供手機／桌機不同尺寸，避免桌機下載超過 1MB 的圖。
  2. 捐款頁壓縮與裁切主視覺（手機可省約 994 KiB）。關於我們查清 22.1s 的 LCP 元素並改成適當解析度。
  3. Noto Sans TC 自架 subset，正式站建議只留實際使用的字重（通常 400、700）。不要用 Google Fonts CSS 一次拉 300／400／500／700 與大量拆檔。
  4. 所有 img（含 logo.svg）補 width／height 或 aspect-ratio。
P1 伺服器

第三階段：TTFB 與主執行緒

  1. 匿名使用者 HTML 快取（Drupal Internal Page Cache / Dynamic Page Cache）與 CDN。捐款等動態表單頁可排除強制全頁快取，但靜態列表與內容頁必須快取。
  2. 非首屏 JS（Slick、extlink、Google CSE、jQuery 相關）defer。活動、年度報告的 TBT 偏高，應一併檢查。
  3. 回測頁面：首頁、捐款、議題觀點庫、活動、關於我們。這五頁涵蓋主視覺、表單、列表、內容四種模板。

五、驗收標準（建議寫進工單）

為什麼要分成兩關 Chrome UX Report 是近 28 日滾動平均，上線當天無法用實測 INP／TTFB 驗收。上線當週只驗「做了沒」與實驗室對照；實測等到滿 28 天再看。PSI 0–100 分不列入通過與否，單次實驗室分數允許波動。

六、不建議寫進工單的項目

項目原因
把每頁手機 PSI 分數做到 90+在 Drupal + GTM 架構下不務實，也不是 Google 排名條件。總分不列入驗收。
上線當天用實測 INP／TTFB 驗收CrUX 是 28 日平均，當天數字幾乎不會變。
INP 必須 ≤150ms、TTFB 必須 ≤800ms 才算過可當加分目標；硬性合格見上一節關卡 A／B。
Minify CSS／JS 當獨立工項節省只有數十 KiB，aggregation 做好就會附帶處理。
修復 Facebook fbevents 的 Legacy JavaScript第三方程式碼，應延後或移除 Pixel，而不是改寫。
為實驗室 CLS 0.537 重做首頁版型真實使用者 CLS 已是 0；修字體與圖片尺寸即可。
Agentic Browsing 0/2實驗性類別，與搜尋排名與使用者體驗無關。
需求摘要 全站被 Drupal 主題在 head 載入數十個 CSS、Google Fonts 多字重，以及 GTM、gtag、Facebook、Matomo 同時載入拖慢。請先做 CSS 合併／按頁載入、LCP 圖片、第三方延遲與 HTML 快取。上線當週：回測頁手機 LCP 降到 4 秒以內、工程清單完成。滿 28 天：實測維持 Passed，INP 不掉出良好，TTFB 至少降到 1.0s 以內。
